## v1 Requirements — All Complete

### Logging

- [x] **LOG-01**: User can tap a "Woke up" quick-log button that records a wake event at the current time, rounded to 5 minutes. *(Phase 1 — `today-screen.js` BUTTONS[0]; e2e `reload.spec.js`)*
- [x] **LOG-02**: User can tap a "Going to sleep" quick-log button that records a bedtime event at the current time, rounded to 5 minutes. *(Phase 1)*
- [x] **LOG-03**: User can tap a "Nap start" quick-log button that records a nap-start event at the current time, rounded to 5 minutes. *(Phase 1)*
- [x] **LOG-04**: User can tap a "Nap end" quick-log button that records a nap-end event at the current time, rounded to 5 minutes. *(Phase 1)*
- [x] **LOG-05**: User can manually enter or edit any event time via a form (date + time picker) for the current day or any past day. *(Phase 1 — `manual-entry.js` + future-date guard)*
- [x] **LOG-06**: User can delete a logged event from history. *(Phase 1 — `event-log.js:151-157`)*
- [x] **LOG-07**: All event times are captured, stored, and displayed at 5-minute precision. *(Phase 1 — `roundTo5` chained in every write path)*
- [x] **LOG-08**: Events that belong to the same subjective night/day are grouped under one "day" record using a configurable cutover hour (default ~04:00). *(Phase 1 — `day-bucket.js` + cutoverHour injection)*
- [x] **LOG-09**: Each day record contains at most one nap (a single start/end pair). *(Phase 1 — `extraNaps` overflow with `extra:true` shallow copy; Plan 01-06)*

### Configuration

- [x] **CFG-01**: User can set a single subject profile display name in Settings. *(Phase 2 — `header.js:38`; DEFAULT_SETTINGS.subjectName='Baby')*
- [x] **CFG-02**: User can configure `max_delta` in Settings. *(Phase 2 — Settings modal; round-trip E2E)*
- [x] **CFG-03**: User can configure `min_days` in Settings. *(Phase 2 — Settings modal; round-trip E2E)*
- [x] **CFG-04**: User can toggle automatic outlier detection on/off in Settings. *(Phase 2 — `autoOutlier` checkbox)*
- [x] **CFG-05**: User can manually mark any day as "rejected" (outlier) from the History screen. *(Phase 4 — `history-screen.js` checkbox; `settings.rejectedDays`)*
- [x] **CFG-06**: User can configure the rolling-window length in Settings. *(Phase 2)*
- [x] **CFG-07**: User can choose the statistical blend in Settings — median, mean, or configurable blend. *(Phase 2)*
- [x] **CFG-08**: User can configure the day-cutover hour in Settings (default ~04:00). *(Phase 2 — `today-screen.js` passes `snap.cutoverHour` to `daysBySubjectiveNight()`)*
- [x] **CFG-09**: User can toggle between 24-hour and 12-hour time format in Settings. *(Phase 2 — `formatTime`/`to24h`/`to12h`; 5 E2E specs)*

### Prediction

- [x] **PRED-01**: User sees a forecast for the next wake-up time, shown as a central time plus a min/max band. *(Phase 3 — `forecast.js`; unit group 5; E2E test 2)*
- [x] **PRED-02**: User sees a forecast for the next bedtime, shown as a central time plus a min/max band. *(Phase 3)*
- [x] **PRED-03**: User sees a forecast for the next nap start, shown as a central time plus a min/max band. *(Phase 3)*
- [x] **PRED-04**: User sees a forecast for the next nap end, shown as a central time plus a min/max band. *(Phase 3)*
- [x] **PRED-05**: When a prediction's ±delta exceeds max_delta, the app replaces the point + band view with a probability band over time. *(Phase 3 — `generateProbabilityBand()`; unit group 10; E2E test 4)*
- [x] **PRED-06**: Forecasts are hidden until at least `min_days` of valid history exist; explicit cold-start message shown instead. *(Phase 3 — `detectColdStart()`; unit groups 11–13; E2E test 1)*
- [x] **PRED-07**: Forecasts update automatically whenever the user logs a new event or toggles a day's `rejected` flag. *(Phase 3 — `eventLog.subscribe()` + `settings.subscribe()` wired in today-screen)*

### Screens

- [x] **UI-01**: "Today + Forecast" landing screen shows the next four predicted events with bands plus the four quick-log buttons. *(Phase 3 — `today-screen.js`; E2E test 2)*
- [x] **UI-02**: "Today + Forecast" landing screen surfaces a prominent "next event" card. *(Phase 3 — `renderNextEventCard()`; E2E test 5)*
- [x] **UI-03**: "History" screen shows a scrollable table of past days with per-row edit, delete, and "rejected" toggle controls. *(Phase 4 — `history-screen.js`; 23 E2E tests)*
- [x] **UI-04**: "Charts" screen displays sleep length over time, wake- and sleep-time bands, nap pattern, activity correlation, and a calendar heatmap. *(Phase 7 — `charts-screen.js`; 5 SVG visualizations)*
- [x] **UI-05**: "Accuracy" screen shows three success-rate metrics side-by-side. *(Phase 7 — `accuracy-screen.js`; 4×3 grid; E2E spec)*
- [x] **UI-06**: User can navigate between Today, History, Charts, and Accuracy from any screen. *(Phase 7 — bottom nav; `applyTabVisibility()` in `app.js`)*

### Data Lifecycle

- [x] **DATA-01**: User can export the full dataset as a structured JSON file downloaded via the browser. *(Phase 5 — `settings-modal.js` export flow; download via Blob)*
- [x] **DATA-02**: User can import a previously exported JSON file with lossless round-trip. *(Phase 5 — `handleJsonImport`; E2E JSON round-trip test)*
- [x] **DATA-03**: User can import a CSV file matching the known column schema. *(Phase 5 — `csv-parse.js`; BOM strip, DD-MM-YYYY, fuzzy headers)*
- [x] **DATA-04**: App state is cached in localStorage so the app survives reloads and offline use. *(Phase 1 — `storage-local.js`; E2E `reload.spec.js`)*
- [x] **DATA-05**: Exported JSON is treated as canonical truth; localStorage acts as a cache. *(Phase 5 — `eventLog.replace()` on import; `storage.save()` seam)*

### Life Stages

- [x] **STAGE-01**: User can mark a date range as a named "stage" to segment historical data. *(Phase 6 — `settings.stages[]`; Stages CRUD in Settings modal)*
- [x] **STAGE-02**: User can scope the forecast to use only data from the current stage. *(Phase 6 — `filterDayRecordsByStage()` called in `today-screen.js` before `forecast()`)*

### Platform

- [x] **PLAT-01**: App is built with vanilla HTML/CSS/JS only — no frameworks, no build step, no npm dependencies. *(Phase 8 — automated check; 08-05 SUMMARY)*
- [x] **PLAT-02**: Code is split across multiple HTML/CSS/JS files. *(Phase 8 — 33 JS source files across `lib/`, `store/`, `ui/`, `adapters/`)*
- [x] **PLAT-03**: App installs as a PWA (manifest + service worker) and works fully offline, including from `file://`. *(Phase 8 — `manifest.json`, `sw.js`, `app.js` file:// guard)*
- [x] **PLAT-04**: App is deployable to GitHub Pages with no server-side code. *(Phase 8 — `ci.yml` actions/deploy-pages@v4)*
- [x] **PLAT-05**: UI text is English only. *(Phase 8 — automated check: no Polish user-facing strings in `js/ui/`)*
- [x] **PLAT-06**: App has its own visual identity — calm dark/minimal/ambient, distinct accent and glyph set. *(Phase 8 — `@keyframes drawLine/fadeInEl`; stroke SVG icons; 5-group settings modal)*
- [x] **PLAT-07**: All notifications are surfaced in-app only — no browser or OS push notifications. *(Phase 8 — automated check: no PushManager/showNotification in `js/`)*
- [x] **PLAT-08**: App logic is unit-testable via Node's built-in `node:test`. Tests live in `tests/unit/`. *(Phase 1 — 495 pass at Phase 8 gate)*
- [x] **PLAT-09**: App is structured into pure-logic modules with thin adapters for DOM, localStorage, and system clock. *(Phase 1 — `js/{lib,store,adapters,ui}` split; composition root in `app.js`)*
- [x] **PLAT-10**: App has end-to-end UI tests using Playwright as a dev-only dependency. *(Phase 1 — `@playwright/test` devDependency only; `tests/e2e/`)*
- [x] **PLAT-11**: Project follows TDD as its primary development discipline. *(Phase 1 — RED→GREEN commit pairs; D-22 matrix audited)*
