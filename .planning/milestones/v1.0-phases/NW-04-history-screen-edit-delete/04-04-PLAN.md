  <files>js/ui/history-screen.js</files>
  <action>
    **What:** Activate the rejected checkbox in each day row. When toggled, update settings.rejectedDays list and call settings.update() to persist the change.

    **Implementation:**
    1. For each day row, create a checkbox input element:
       ```javascript
       const checkbox = el('input', {
         type: 'checkbox',
         checked: day.rejected ? 'checked' : '',
         'aria-label': `Mark ${day.date} as rejected`,
         'data-date': day.date,
       });
       ```

    2. Attach a change listener:
       ```javascript
       checkbox.addEventListener('change', (e) => {
         const dayDate = e.target.getAttribute('data-date');
         const isNowRejected = e.target.checked;
         
         // Get current rejected days from settings
         const currentRejected = settings.get().rejectedDays || [];
         let newRejected = [...currentRejected];
         
         if (isNowRejected) {
           // Add date if not already present
           if (!newRejected.includes(dayDate)) {
             newRejected.push(dayDate);
           }
         } else {
           // Remove date
           newRejected = newRejected.filter((d) => d !== dayDate);
         }
         
         // Persist to settings
         settings.update({ rejectedDays: newRejected });
         // Subscriber fires; table re-renders with updated rejection state
         // Today screen forecast re-computes with downweighting applied
       });
       ```

    3. Per D4-05: Toggle is immediate; no confirmation needed (unlike [delete]).

    4. Per D4-14: No validation. User can toggle any day, any time (no constraints).

    5. Per D3-12: When settings.update() is called, settings subscriber fires → History screen's subscriber callback fires → table re-renders with updated day.rejected values (from day-bucket, Wave 1) → row opacity updates accordingly.

    6. Also per D3-12: Forecast subscriber fires → forecast re-computes with downweighting → Today screen updates.

    **Checkbox styling:** Use semantic HTML `<input type="checkbox">`. CSS will style it (Task 2).

    **Accessibility:** Include `aria-label` describing which day is being toggled. Role is implicit (checkbox input).

    **Per RESEARCH §Pitfall #3 (Rejected Flag Storage):** Wave 1 chose to store rejectedDays as a list in settings. Day-bucket (Wave 1) computes day.rejected by checking if the date is in the list. No new storage changes needed here; just update the list.

    **Edge case: Duplicate dates in rejectedDays**
    - If the list somehow has duplicates (e.g., from an import or prior bug), use `Set` to deduplicate:
      ```javascript
      const uniqueRejected = [...new Set(newRejected)];
      ```
    - Not strictly necessary (Phase 1 prevents duplicates), but defensive.

    **## Phase 4: History Screen & Edit/Delete**

    ### Features Implemented

    - **History Screen:** Day-column table showing all past sleep events (date, wake, bedtime, nap start/end, rejected flag, actions)
    - **Navigation:** Two-tab header navigation (Today | History) allowing seamless switching between screens
    - **Edit Events:** Click [edit] on any event time to open the manual-entry modal and modify date/time; changes persist and trigger forecast re-compute
    - **Delete Days:** Click [delete] on a day row to remove all events for that date; includes confirmation dialog
    - **Reject Outliers:** Toggle a checkbox on any day to mark it as rejected (outlier); rejected days are visually grayed at 50% opacity and downweighted at 0.5x in forecast calculations
    - **Reactive Updates:** All mutations (edit, delete, reject) trigger immediate forecast re-computation via the subscriber pattern from Phase 3

    ### Design Decisions

    - **Rejected-Day Storage (D4-05):** Rejected days are stored as a list of date strings in `settings.rejectedDays` (not per-event). This keeps the model simple and leverages the existing settings-store subscription pattern. Day-bucket computes the derived `day.rejected` boolean on every render.
    - **Delete Scope (D4-06):** Deleting a day removes all events for that calendar date (wake, bedtime, nap, extra naps if present). This matches the day-grouping logic in daysByCalendar().
    - **Tab Persistence (D4-08):** Tab state (Today vs. History) is in-memory only; does not persist across reload. This keeps the code simple for Phase 4. Phase 8 (PWA hardening) can add deep-linking if needed.
    - **Edit Validation (D4-13):** Reuses Phase 1's manual-entry validation (5-min rounding, future-date guard). This prevents new validation logic and ensures consistency with the main log entry flow.
    - **Forecast Timing (D4-09):** Forecast re-computes only on Save (not during edit), ensuring a clean and predictable user experience.

    ### Testing Coverage

    - **Unit Tests:** db-shape.js tests schema migration (rejectedDays field); day-bucket.js tests rejection-boolean computation
    - **Integration Tests:** edit-delete-flow.test.js verifies that eventLog mutations trigger subscribers and forecast re-computes correctly

    - **Manual Verification Checkpoint:** Human verification of tab switching, table display, edit/delete/reject workflows, and forecast updates

    ### Known Constraints & Future Work

    - **Scroll Position:** When returning to History after editing, the table scrolls to top (no scroll-position restoration). Phase 8+ could add scroll caching if needed.
    - **Bulk Edit:** Phase 4 edits events one-at-a-time. Phase 7+ could offer day-wide bulk edit if users request it.
    - **Rejection Metadata:** Rejected days are not annotated with reason (manual vs. auto-detected). Phase 7's accuracy dashboard can add rejection history and metadata.
    - **Multi-Nap Display:** Phase 4 shows only the primary nap slot in the table. Extra naps can be edited individually but are not surfaced as separate columns. Phase 5+ can expand if needed.
    - **Browser Undo:** Deletes are reversible via Ctrl+Z (browser undo). No in-app undo stack. Phase 7+ can add explicit undo/restore UI alongside the accuracy dashboard.

    - **Future Phase 5 (Import/Export):** Rejected days in settings are included in exported JSON; imported data will restore rejection state
