  <files>js/ui/history-screen.js</files>
  <action>
    **What:** Create a new module `js/ui/history-screen.js` that exports a `mountHistoryScreen({ root, eventLog, settings })` function. This function renders a day-column table and sets up reactive subscriptions.

    **Table structure (per D4-01, D4-03):**
    ```
    Date        | Wake  | Bedtime | Nap Start | Nap End | Rejected | Actions
    2026-06-05  | 07:00 | 21:30   | 14:15     | 14:45   | [ ]      | [Edit] [Delete]
    2026-06-04  | 07:10 | 21:45   | —         | —       | [✓]      | [Edit] [Delete]
    ...
    ```

    **Implementation:**
    1. Call `eventLog.daysByCalendar(Infinity)` to fetch all days (Wave 1 ensures settings parameter is supported)
    2. Sort days descending (most recent first) — already handled by daysByCalendar per D4-02
    3. For each day, render a `<tr>` with cells:
       - Date: `day.date` (YYYY-MM-DD format, no transform)
       - Wake, Bedtime, Nap Start, Nap End: Use `formatTime(event.at, settings.get().timeFormat)` if event exists, else "—"
       - Rejected: `day.rejected` (will wire checkbox toggle in Wave 3)
       - Actions: Placeholder cells (will add [Edit] [Delete] buttons in Wave 3)
    4. Apply rejected-row styling: if `day.rejected`, add `class="rejected"` to the row (CSS handles opacity in Task 4)
    5. Empty state: If `dayRecords.length === 0`, show message "No events logged yet. Go to Today to log your first sleep event." (per CONTEXT "Empty History message")

    **Subscription pattern (per D3-12 + RESEARCH §Pattern 1):**
    - Define `const render = () => { /* re-fetch days + re-render */ }`
    - Subscribe: `eventLog.subscribe(render)` and `settings.subscribe(render)`
    - Each subscription calls `render()` on mutation, ensuring table reflects current state
    - Return unsubscribe functions for cleanup (optional; app.js will handle)

    **Component contract:**
    - Input: `root` (DOM element to mount table into), `eventLog` (store), `settings` (store)
    - Side effects: Mutates root's children; sets up subscribers
    - Output: Day-column table HTML, fully rendered and reactive

    **Per RESEARCH §Pitfall #1 (stale event references):** Don't cache event objects. Each render fetches fresh data from eventLog.

    **Per RESEARCH §Pitfall #3 (rejected flag storage):** day.rejected is computed by day-bucket in Wave 1 from settings.rejectedDays. No special handling needed here; just render the boolean.

    **Time formatting:** Use the helper from Phase 2: `import { formatTime } from '../lib/time.js'`. Pass the user's timeFormat setting from `settings.get().timeFormat`.

    **Styling:** Mark table cells and rows with semantic classes (`.historyTable`, `.day-row`, `.rejected`, `.day-date`, `.day-wake`, etc.) for CSS targeting in Task 4.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Day records to table HTML | Day records come from eventLog (trusted store). Table renders via `textContent` (never `innerHTML`), preventing XSS. |
| User click on tab → activeTab state | Tab clicks are DOM events (user-controlled, in-app only). Updating activeTab is safe; no external input. |
| Subscription callbacks | eventLog and settings subscribers are internal (no third-party callbacks). Re-renders are deterministic. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-04 | Tampering | History table HTML rendering | mitigate | Use `textContent` (never `innerHTML`) for dynamic values (times, dates). Times are formatted by Phase 2's `formatTime()` (trusted helper). Event IDs in `data-event-id` are opaque strings; no user input. |
| T-04-05 | Information Disclosure | Rejected day visibility | mitigate | Rejected days are visually marked at 50% opacity (per D4-10). Data remains visible; no hidden information. User can audit which days are rejected by scrolling History. |
| T-04-06 | Denial of Service | Large table rendering | accept | Phase 4 assumes <365 days of history (typical user). Rendering all rows is O(n); acceptable for Phase 4. Phase 8+ can optimize with pagination or virtual scrolling if needed. |

</threat_model>
