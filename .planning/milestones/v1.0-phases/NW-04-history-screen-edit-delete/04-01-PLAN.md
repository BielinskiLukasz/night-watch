  <action>
    **What:** Both daysByCalendar() and daysBySubjectiveNight() build and return day records. Each returned day record must include a `.rejected: boolean` field computed as `settings.rejectedDays.includes(day.date)`.

    **Signature change:** These functions are called from the History screen (Wave 2+) and forecast engine (Phase 3). Modify the day-bucket module to accept a `settings` parameter (or inject it as a closure), so it can compute the rejection boolean at render time.

    **Current state:** daysByCalendar and daysBySubjectiveNight in day-bucket.js are pure functions that take events and cutoverHour. They do not currently know about settings. Modify them to accept settings as an optional parameter and compute day.rejected for each day. If settings is not provided (legacy Phase 1/2 callers), default to `day.rejected = false` for backward compat.

    **Derived vs. stored:** The day.rejected field is NOT stored on events; it is derived at render time from the settings.rejectedDays list. This keeps the canonical source (settings) singular and avoids sync issues.

    **Example:**
    ```javascript
    export function daysByCalendar(events, limit, settings) {
      const days = _groupByCalendarDate(events);
      return days
        .slice(0, limit)
        .map(day => ({
          ...day,
          rejected: settings && settings.rejectedDays.includes(day.date),
        }));
    }
    ```

    **Per D4-01, D4-02:** Day rows are most-recent-first (descending). The day-bucket already handles this; rejected computation does not change ordering.

    **Test targets:**
    - Unit test: daysByCalendar returns day records with .rejected = true when settings.rejectedDays includes the date
    - Unit test: daysByCalendar returns day records with .rejected = false when the date is not in rejectedDays
    - Unit test: empty settings.rejectedDays means all days have .rejected = false
    - Unit test: adding/removing dates from settings.rejectedDays re-computes rejection state on next call (no caching)
  </action>

| Settings input → day.rejected boolean | Settings are user-editable (Phase 2) or manually toggled (Phase 4 History). No untrusted external source; local mutation only. |
| Day date string in rejectedDays | Date strings come from day.date field (derived from event.at). No user free-form input; format is YYYY-MM-DD (enforced by day-bucket). |

| Threat ID | Category | Component | Disposition | Mitigation Plan |

| T-04-01 | Integrity | settings.rejectedDays array mutation | mitigate | settings.update() enforces immutable update pattern (returns new object, not mutation). Defensive copy on read via settings.get(). No direct array reference exposure. |
| T-04-02 | Integrity | Day record .rejected field computed at render time | mitigate | day.rejected is not persisted; it is derived from settings on every call. No stale state risk. |
| T-04-03 | Availability | Large rejectedDays array linear search | accept | In Phase 4, expect <100 rejected days for a typical user (years of data). Linear search via .includes() is acceptable. Phase 8+ can optimize with Set if needed. |
