Close UAT Gaps 2 and 3 — both root-caused to `js/ui/manual-entry.js` lines 90–119's onClose validator: (a) no future-date guard (Gap 2, major) and (b) silent `return` on every rejection branch (Gap 3, major). **Phase Goal (user story):**

**As a** Nightwatch user logging or correcting past events, **I want to** know immediately when my input is invalid (future date, out-of-range hour, missing field) — with a message that points at the field I need to fix — **so that** I never wonder whether Save worked, and **so that** I can't accidentally pollute the event log with future-dated entries that Phase 3 forecast would treat as real.

**Purpose:** Today the validator silently bails on every rejection (`return` with no user feedback) AND has no future-date check at all. From the user's chair: future timestamps slip through; out-of-range inputs vanish into nothing. Both undermine the user's trust in the Add/Edit modal. The fix refactors `onClose` into a pure `validate(input, { now })` function + a thin UI handler that renders errors inline and only closes the dialog on success.

**Source of decisions:** `01-UAT.md` Gaps 2 (test 5) and 3 (test 9) — both with proposed remediation paths spelled out. CLAUDE.md "No `.innerHTML = ` with non-empty data (T-07)" — error rendering must use textContent. `01-05-SUMMARY.md` clock-adapter seam (D-07 / T-04) — pure `validate()` takes an injected `now` so the test path is deterministic without setting `globalThis.localStorage` or stubbing `Date`.

**Why bundle Gaps 2 + 3:** They share the same validator function and the same modal close path. Splitting them into separate plans would mean two consecutive edits to the same lines of `manual-entry.js` + double the test setup. One coordinated change is cleaner and lower risk than two sequential ones.
</objective>
