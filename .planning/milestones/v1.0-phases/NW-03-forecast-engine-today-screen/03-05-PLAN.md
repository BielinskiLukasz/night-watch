<task type="auto">
  <name>Task 3: Document forecast algorithm in README.md</name>
  <files>README.md</files>
  <action>
    Add or update the README.md with a "Forecast Algorithm" section covering:
    
    **Section: Forecast Algorithm**
    - High-level overview: "Predictions use empirical CDF percentiles (10th–90th) of a rolling window of past events."
    - Input: event history + settings (minDays, maxDelta, windowDays, statBlend)
    - Output: predictions for four event types (wake, bedtime, nap start, nap end), each with central time + min/max band (or probability band if high-uncertainty fallback active)
    - Step-by-step:
      1. Cold-start gate: if < minDays valid days, suppress predictions and show "Log N more days" message
      2. Extract events of each type from the rolling window (default 7 days)
      3. Sort times numerically (converted to minutes-since-midnight)
      4. Apply downweighting: rejected days count at 0.5× for percentile math
      5. Calculate percentiles: P10 (min), P50 (central), P90 (max) using linear interpolation
      6. Check confidence: if band width (P90 - P10) > maxDelta, switch to probability-band fallback
      7. Return predictions with selected UI mode (min/max band or probability table)
    
    **Subsection: Configuration Tuning**
    - `minDays` (default 7): minimum days of history before forecasts appear
    - `maxDelta` (default 30 min): confidence-band width threshold; exceeding triggers probability-band fallback
    - `windowDays` (default 7): rolling-window length for percentile calculation
    - `statBlend` (locked to 'median' in Phase 3): statistic used as central prediction (future Phase 7 will allow mean/blend)
    - `autoOutlier` (stored but inert in Phase 3): automatic outlier detection (Phase 3+ will implement)
    
    **Subsection: Reactive Updates**
    - Predictions re-compute synchronously whenever user logs a new event or toggles a day's "rejected" flag
    - No debounce or caching in Phase 3; compute-on-demand is fast enough for typical history size (7–365 days)
    - Subscribe pattern: Today screen listens to eventLog and settings changes via `eventLog.subscribe()` and `settings.subscribe()`
    - Each subscriber callback: `days = eventLog.daysBySubjectiveNight(...); predictions = forecast(days, settings.get()); renderUI(predictions)`
    
    **Subsection: Next-Event Selection (Cycle-Aware Priority)**
    - The "next event" hero card uses sleep-cycle awareness to pick which prediction is most imminent and intuitive
    - Priority depends on the most recently logged event type:
      - Last logged = bedtime → next is wake
      - Last logged = wake → next is nap start
      - Last logged = nap start → next is nap end
      - Last logged = nap end → next is bedtime
    - Within a tier, earliest-by-central-time prediction wins
    - This heuristic matches the natural rhythm of a child's day (wake → nap → bedtime → wake)
    
    **Subsection: Uncertainty Modeling**
    - When prediction band is tight (±delta ≤ maxDelta), show central time + min/max band
    - When prediction band is wide (±delta > maxDelta), switch to probability-band fallback:
      - Display cumulative probability at 5-minute intervals: "P(wake by 06:30) = 20%, by 06:45 = 50%, by 07:00 = 85%"
      - This honestly surfaces uncertainty instead of claiming false precision
    
    **Subsection: Missed Predictions**
    - If a forecasted central time is in the past (e.g., forecast was 07:00 but it's 08:15), the card is grayed out and labeled "Missed by 75min"
    - Missed cards remain visible for parent's reflection on accuracy; Phase 7 accuracy dashboard will expand on this theme
    
    Reference Code Examples from RESEARCH.md for those interested in implementation details.
