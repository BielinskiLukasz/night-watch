    (1) In the open handler (where form fields are pre-populated from the event being edited, or cleared for new entry):
    - After existing form field population, add:
      ```javascript
      const eventDate = /* the calendar date of the event being edited/created, as YYYY-MM-DD */
        /* For new: derive from the form's current date field value, or default to today */
        /* For edit: existing.at.slice(0, 10) */
      const intenseDayCheck = form.elements.namedItem('intenseDay');
      if (intenseDayCheck) {
        const currentIntense = settings.get().intenseDays || [];
        intenseDayCheck.checked = currentIntense.includes(eventDate);
      }
      ```
    - NOTE: the eventDate must be derived from the same `at` string that is being edited. For new events, the date input is not yet filled at open-time — pre-check should use the form's date value if available, or leave unchecked (the user sets the date then can check the box).
    - Simplification: derive date from the event's `at` field when editing. For new events, read the date input's value at save time (not at open time) since the user may change it.

    (2) In the save/close handler (after eventLog mutation, before dialog close or return):
    - Add:
      ```javascript
      const intenseDayCheck = form.elements.namedItem('intenseDay');
      if (intenseDayCheck) {
        const savedDate = form.elements.namedItem('date').value; // YYYY-MM-DD from date input
        const current = settings.get().intenseDays || [];
        if (intenseDayCheck.checked) {
          if (!current.includes(savedDate)) {
            settings.update({ intenseDays: [...current, savedDate] });
          }
        } else {
          if (current.includes(savedDate)) {
            settings.update({ intenseDays: current.filter(d => d !== savedDate) });
          }
        }
      }
      ```
    - Read-before-write: always call `settings.get().intenseDays` immediately before mutating to avoid stale reference (store does internal read-before-write too, but be explicit per PATTERNS.md §Store read-before-write).
    - Guard: only call settings.update when the state actually changed (checked && not in list, or unchecked && in list) — avoids spurious subscriber notifications.
