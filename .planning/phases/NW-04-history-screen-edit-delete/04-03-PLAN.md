  <name>Task 2: Add [delete] button per day row; wire window.confirm() and deleteEvent() for all events in the day</name>
  <files>js/ui/history-screen.js</files>
  <action>
    **What:** Add a [delete] button for each day row. Clicking it shows a confirmation dialog. On confirmation, all events for that date are deleted from the event log.

    **Button placement:**
    - Per D4-01, the "Actions" column already exists; add [delete] button alongside [edit] buttons or in a separate cell
    - Add a data attribute: `data-date={day.date}` to identify which day to delete

    **Implementation:**
    1. For each day in dayRecords, create a [delete] button at the row level
    2. Attach a click listener:
       ```javascript
       deleteBtn.addEventListener('click', (e) => {
         e.preventDefault();
         const dayDate = deleteBtn.getAttribute('data-date');
         const confirmed = window.confirm(
           `Delete all events for ${dayDate}? This cannot be undone.`
         );
         if (!confirmed) return;
         
         // Delete all events for this date
         const eventsForDay = eventLog.listEvents().filter(
           (ev) => ev.at.slice(0, 10) === dayDate
         );
         for (const event of eventsForDay) {
           eventLog.deleteEvent(event.id);
         }
         // Subscribers fire; table re-renders; forecast updates
       });
       ```

    **Confirmation message (per D4-06):**
    - Use window.confirm() (standard browser dialog, Phase 1 pattern)
    - Message: "Delete all events for {date}? This cannot be undone."
    - On OK: proceed with deletion
    - On Cancel: no-op

    **Deletion scope (per RESEARCH §Open Question #2 resolution):**
    - Delete all events whose `at.slice(0, 10) === day.date`
    - This includes wake, bedtime, nap-start, nap-end, and any extra naps (if Phase 1 UAT gap 4 added them)
    - All events for that calendar date are removed

    **Per D4-11:** Deletion is immediate but reversible via browser undo (Ctrl+Z). No custom undo/restore UI (deferred to Phase 7).

    **After deletion:**
    - deleteEvent() is called for each event (idempotent per Phase 3)
    - notifySubscribers() fires after each delete
    - History table re-renders (row for that date disappears)
    - Today screen forecast re-computes (D3-12, D4-09)
    - If the deleted day was the last day with data, History shows empty-state message

    **Edge case: Rapid delete**
    - If user clicks [delete] twice quickly, the second click may find no events for that date (already deleted)
    - deleteEvent() is idempotent; calling it on a missing id returns false (no throw)
    - The loop gracefully handles this (no events to delete, loop is empty)

    **Visual feedback:**
    - Per Claude's Discretion in CONTEXT: Row can fade out smoothly (200–300ms animation) or disappear instantly
    - For Phase 4, instant removal is acceptable (simple, predictable)
    - CSS can be added in later phases if smooth deletion is desired

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| User click → editEvent/deleteEvent | DOM events from user interactions. Wiring is internal; no external input enters the store. |
| Event ID from data attribute → event lookup | Event IDs are opaque strings generated by Phase 1. Used only for lookup in eventLog; validated by store (throws if not found). |
| Modal onSave callback → editEvent patch | Modal validates and normalizes data before onSave fires. Patch is { type, at }; both are validated by editEvent (re-rounds, re-validates). |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-07 | Tampering | Event ID in data attribute → stale reference | mitigate | Always re-fetch event before opening modal (Task 1 code example). Store throws "Event not found" if ID is missing. Graceful no-op in UI. |
| T-04-08 | Integrity | User confirms delete, then cancels — orphaned listeners | mitigate | window.confirm() is synchronous. If user cancels, loop doesn't execute. No state change. |
| T-04-09 | Disclosure | Deleted events visible in browser devtools | accept | Deleted events are removed from localStorage and eventLog (in-memory). Devtools can see the current localStorage state; no sensitive data exposure (only sleep times, no PII beyond subject name). |

</threat_model>
