**Wave 1b: Store replace() API**

Add a replace(blob) method to both createEventLog() and createSettingsStore() so the import handler (Waves 2–3) can atomically swap in-memory state, persist, and trigger subscriber re-renders in one call. Write a failing integration test first (RED), then implement (GREEN).

**Purpose:** DATA-02 (JSON round-trip import) and DATA-05 (file-as-truth) require a mechanism to replace the full in-memory state from an imported blob without destroying existing subscriber registrations. Re-initializing stores would lose the subscriptions established by app.js at boot time. replace() mutates the shared db in place and fires existing subscribers — the same approach used by addEvent/update.

**Output:** replace(blob) on both stores, integration test confirming the subscriber chain fires correctly after replace(), no regressions in existing store tests.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Imported blob → replace(blob) | Parsed JSON from user file (untrusted) is passed to both stores |
| replace() → storage.save() | In-memory state overwrites localStorage; must be migrated and validated before write |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-02-01 | Tampering | replace(blob) with future schema version | mitigate | migrateV1ToV2 throws on version >= 3; replace() propagates the error so the UI import handler can show "Incompatible file — exported by a newer version of Nightwatch" (per D5 Claude's Discretion) |
| T-05-02-02 | Tampering | replace(blob) with null settings slice | mitigate | settings.replace() calls validateSettings(db.settings ?? {}, {mode:'load'}) which normalizes missing fields to defaults; no raw null reaches store subscribers |
| T-05-02-03 | Integrity | Cross-store ordering race (eventLog.replace before settings.replace) | mitigate | Both replace() calls use storage.save(db); the second save wins and carries both stores' updated state. The import handler (Plan 05-04/05) calls storage.save(migratedBlob) once before both replace() calls per RESEARCH §Pattern A call sequence, ensuring consistent state |
  | T-05-02-04 | Denial of Service | Very large events array in imported blob | accept | No practical size limit in Phase 5; localStorage has a ~5MB limit that acts as a natural cap. Phase 8 can add size warnings. |
| T-05-02-SC | Tampering | npm/pip/cargo installs | mitigate | No new runtime dependencies; store files are pure vanilla JS |
</threat_model>
