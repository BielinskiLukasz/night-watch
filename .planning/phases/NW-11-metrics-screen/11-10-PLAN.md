  <name>Task 1: Analyze day-bucket bucketing and update date attribution in aggregateMetrics (G-NW-11-21, G-NW-11-22)</name>
  <files>js/lib/metrics.js, js/lib/day-bucket.js</files>
  <action>Address the overnight sleep issue by understanding and fixing the bucketing and date attribution logic.

**Analysis:**
The day-bucket.js cutover rule (lines 97-104) groups events by calendar date using a cutover hour (default 04:00). A bedtime at 22:30 on 31.03 (>= 04:00) stays on 31.03. A wake at 07:30 on 01.04 (>= 04:00) stays on 01.04. This splits the overnight sleep into two separate day buckets: one with only bedtime, one with only wake.

**Root Cause:**
The bucketing works correctly for the TIF algorithm (which is event-centric). But for the Metrics screen (which is day-centric), the split creates an issue: the 31.03 bucket has bedtime but no wake, and the 1.04 bucket has wake but no bedtime. The aggregateMetrics function must handle this by:
1. Pairing bedtime from 31.03 with wake from 01.04 to calculate sleep duration
2. Attributing the combined sleep record to the 01.04 row (wake date)

**Fix Strategy:**
In aggregateMetrics (metrics.js, starting around line 166), modify the logic to:
1. When processing a day with bedtime but no wake, look ahead one calendar date to find the matching wake
2. Calculate sleepDuration as: extractTime(next day's wake) - extractTime(current day's bedtime), accounting for midnight crossing
3. Attribute the row to the next calendar date (the wake date) using the corrected date attribution logic already in place (lines 175-184)

**Implementation:**
Modify aggregateMetrics to accept and process day records that span calendar dates:
- When a day has bedtime but no wake, check if the immediately following day (in the sorted array) has a wake and its date is the next calendar date
- If found, pair the bedtime from the current day with the wake from the next day for sleep duration calculation
- Use the next day's date as the row date
- Ensure the sleep row is attributed to the wake date and includes all metrics computed with this paired sleep duration

**Edge Cases:**
- Last day with bedtime but no wake → no following day to pair with → keep bedtime only, attribute to bedtime date+1
- Multiple days with missing wakes → handle each sequentially
- Day with no wake and no bedtime → skip or handle as needed per existing logic</action>
