<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| App ↔ IndexedDB | `createIndexedDbHandleStore` persists a `FileSystemDirectoryHandle` object in the browser's local, same-origin IndexedDB — no network, no cross-origin exposure. |
| App ↔ local filesystem | `saveToDisk` writes to a directory the user explicitly authorized via the native `showDirectoryPicker` dialog — the browser enforces the permission boundary, not this code. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-24-01 | Tampering | restoreHandle (stale/revoked handle) | low | mitigate | `queryPermission`/`requestPermission` branching (D-06) means a revoked or invalid handle is never silently treated as usable — status flows to 'denied', never defaulted to 'granted'. |
| T-24-02 | Information Disclosure | createIndexedDbHandleStore (handle persisted locally) | low | accept | `FileSystemDirectoryHandle` objects never expose a raw filesystem path string (browser design); storage is same-origin IndexedDB with no network egress anywhere in this app. |
| T-24-03 | Denial of Service | saveToDisk (write volume) | low | accept | Write payload is the same bounded JSON blob the existing manual Export JSON path already produces — no new data-volume attack surface introduced. |
| T-24-04 | Spoofing | isFileSystemAccessSupported (fallback misdetection) | medium | mitigate | Feature-detects `showDirectoryPicker` by direct type check only — no `navigator.userAgent` sniffing (see `must_haves.prohibitions`), so a browser cannot be silently misclassified. |

</threat_model>
