**Design-rationale record (why Option B, not Option A, for Gap B):** `js/app.js` calls `restoreHandle().then(...)` asynchronously (an IndexedDB-open + `queryPermission()` chain that always resolves on a later macrotask, never synchronously) and then calls `mountTodayScreen({...})` synchronously a few lines later in the SAME synchronous script execution. `autosaveState.status` is therefore still its initial `'unset'` value at the exact instant `mountTodayScreen` would read it on every page load — even when a previously-picked folder is about to be restored moments later. `today-screen.js`'s banner-construction code (lines 888-925) runs exactly once inside `mountTodayScreen`'s synchronous body, not inside the `render()` function defined later (line 1065) that re-runs on `eventLog`/`settings` changes — so there is no later trigger to re-check an `isConfigured` flag once `restoreHandle()` eventually resolves. Option A (passing `isConfigured` computed from `autosaveState.status` into `mountTodayScreen`'s `autosave` param) would therefore silently fail to suppress the banner on the very case it targets (a folder configured in a *previous* session). Option B avoids this race entirely: it writes the `autosaveBannerDismissed` flag synchronously at the moment of a real, completed, in-session user action (a successful Settings pick), independent of boot-time restore timing, and is read by `today-screen.js`'s existing unmodified gate on the *next* page load.
