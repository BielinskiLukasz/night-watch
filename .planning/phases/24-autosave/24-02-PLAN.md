<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| eventLog mutation ↔ disk write | Every quick-log tap or manual-entry save can now trigger an async filesystem write 500ms later — a new causal chain from "user taps a button" to "bytes hit disk", still entirely local. |
| Settings/Today UI ↔ autosaveActions | The only surface those modules can act through — no direct IndexedDB/File-System-Access access from UI code. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-24-04 | Repudiation | performAutosave error handling | medium | mitigate | Errors are captured into `autosaveState.error`, never caught-and-discarded (see `must_haves.prohibitions` P1) — the user is never left believing an unsaved state is saved. |
| T-24-05 | Elevation of Privilege (browser permission UX) | restoreHandle boot wiring | low | mitigate | `restoreHandle()` runs exactly once, at boot, never from `eventLog.subscribe`/`settings.subscribe` — prevents a permission-prompt-spam pattern that could look like abusive/repeated privilege escalation attempts to the browser and to the user (see `must_haves.prohibitions` P2). |
| T-24-06 | Denial of Service (write storms) | performAutosave concurrency guard | low | mitigate | The `autosaveSaving` boolean prevents two overlapping writes to the same handle; File System Access API implementations reject/throw on concurrent `createWritable()` calls against one file, which this guard avoids triggering. |

</threat_model>
